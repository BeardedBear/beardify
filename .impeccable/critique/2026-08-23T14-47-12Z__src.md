Non-transplantable: BlockAlbums.vue:42-96 (Last.fm rank badge scales with discography length, studio albums only, because Last.fm ranking mixes compilations/live that live in other blocks); CollectionPage.vue:231-266 (tier membership from position + stored sizes); IconButton.vue:44-48 (44px confined to `@media (pointer: coarse)`, motive written in-file: preserve desktop density).

## What is working

1. IconButton.vue - a design-system decision written down. `label` is a required prop so the component cannot render nameless; `aria-hidden` on the glyph for the stated reason (icomoon webfont -> screen reader would announce the private-use codepoint); 44px confined to coarse pointers.
2. BlockAlbums.vue - badge that scales with the discography. ALBUMS_PER_HIGHLIGHT = 4, floor of 3, unranked albums sink rather than interleave ("an unknown play count is not a low one").
3. The share path end to end - recap card, plain-language statement of what the link does and does not grant, precondition, one primary action; receiving page distinguishes 404/403/generic with copy naming the next step; chromeless branch means a stranger does not download the logged-in app.

## Priority issues

### [P0] Every destructive action is one unconfirmed click, and nothing is undoable
AlbumIndex.vue:37/:141 (album), EditPlaylist.vue:41 (whole collection, default-variant button opposite Confirm), PlaylistTracks.vue:59 (track), PlaylistActions.vue:19, PodcastFollowButton.vue:40. Collections are hand-curated over years and unrecoverable from anywhere else (Spotify has no album-playlists). Deleting an album additionally cascades: CollectionPage.vue:255-261 -> shrinkTiersForRemovedAlbums -> writeTierListDescription, silently rewriting stored tier sizes.
Fix: keep the optimistic removal, add Undo to the existing toast (notifications.ts already routes through bearded-ui toast; deleteAlbum already holds the TrackToRemove[] to re-POST). Collection delete needs a real confirm + variant="danger" + separation from Confirm. BdConfirmDialog already exists and is used nowhere.
Command: /impeccable harden

### [P1] 17 icon-only buttons still have no accessible name - the prior audit missed them
BdButton icon-only used 23 times; 17 have no text, no aria-label, no title: SidebarHead (back/forward/search), MobileHeader (menu/search), PageScroller (both arrows), ShareContent (both copies), AlbumHead, SearchInput, QueuedTracks, ArtistHeader, TierEditor, PlaylistTracks, PlaylistActions.
CORRECTION OWED: this session audit reported "17 fixed, 0 remaining". That count covered native `<button>` only and missed BdButton icon-only entirely, which is the majority vector. The post-fix accessibility score of 3/4 was too generous for that reason.
ArtistLinks.vue is the subtlest case: each link has `<span class="link-name">` but it is `display: none` on desktop (:154), removing it from the accessibility tree - so the name is empty despite the opposite intent.
Command: /impeccable harden

### [P1] Loading and empty are conflated: three routes spin forever on an empty list
HomePage, ReleaseListPage, PodcastListPage (inner block) gate BdLoader on `v-if="!list.length"`. HomeStore.ts:49 `catch { // silent fail }`. ReleasesStore.ts:41 has no try/catch at all. AuthPage has neither loading nor error state, only static "Authenticating...".
Only 1 of 13 routes has a real inline error state (SharedCollectionPage). The only written empty state in the product is QueuedTracks.
Command: /impeccable onboard

### [P1] The most-repeated curation gesture is the least-finished screen
AddAlbum.vue:4-19 renders every collection as clickable `<div>`s - no filter, no sort, no keyboard access, font-size-sm at opacity 0.7. Click fires albumAllreadyExist, which recursively paginates the entire target collection with no pending state, no disabled row, no spinner. Copy says "This album allready exists".
Fix: the pattern exists twice already (SidebarIndex.vue:55-63 BdInput + `.filter(lowerName.includes(q))` computed). Lift it. Make rows real `<button>`s. Disable the clicked row with a BdLoader during the check.
Command: /impeccable layout

### [P2] Page inset and grid are decided per file - the flagship surface misaligns at the user own resolution
PlaylistHeader.vue:140 `--header-padd: 5rem`; CollectionPage.vue:337 `--album-list-padd: 10rem`. Between 1201 and 1929px no media query touches both: 70px misalignment between a title and its own content. `@media (--l)` is declared twice in .album-list (356 and 362); the first (4 cols) is dead, so the grid holds at 4 columns from 1201px to 1929px then jumps to 8 - on a 1920px display, four albums per row inside 140px gutters, the density thesis inverted. `--hdpi: 50rem` (PlaylistHeader.vue:157) is dead too, beaten by `--xl: 2rem`.
Background drift: 39 distinct border-radius values, 101 distinct spacing declarations, 0 spacing tokens (font sizes have one).
Fix: one `--page-inset` custom property on the page root consumed by both; delete the duplicate `--l` block; replace fixed column counts with `repeat(auto-fill, minmax(14rem, 1fr))`.
Command: /impeccable layout

## Questions to consider

1. If density is the thesis, why does the grid step 4 -> 8 columns with a 700px dead zone in between?
2. Why is the primary accent spent on "which speaker" rather than "play"? (DeviceList.vue:9 variant="primary" vs transparent PlayerControls.)
3. Is tier structure a property of the collection or of the album set? If the collection, a removal should not collapse it.
4. The sidebar has collection search; the dialog where you actually pick a collection does not. Why did the filter land on the browsing surface and not the deciding one?
5. previous(), Releases, BdConfirmDialog: three things built and unwired. Would an "implemented but unreachable" audit recover more product than any new feature?
